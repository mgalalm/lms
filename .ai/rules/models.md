# Models

## Never name a model/table "Session" — it collides with Laravel's session storage
The product docs call a scheduled tutoring class a "Session," but Laravel's own database session driver (SESSION_DRIVER=database, this project's default) already owns a `sessions` table for login/auth session storage, created in the very first migration. A model/migration named `Session`/`sessions` collides directly with that table.

The tutoring-class concept is modeled as `App\Models\ClassSession` / `class_sessions` table instead. Keep using that name for any future work touching scheduled sessions (Insights, dashboards, Filament resources, etc.) — do not rename back to `Session`.

## Messages are hidden until moderation clears them — never broadcast/query around Message directly
Every Message goes through OpenAI moderation via MessageObserver (created hook) → ModerateMessageJob (ShouldQueue), fail-safe: no OPENAI_API_KEY configured or an API error both resolve to Message::flagModeration() being the *unsafe* default only for genuine API errors — missing config auto-approves (mirrors CreateZoomMeetingJob's "not configured" pattern) so local/test envs without a key aren't broken. QUEUE_CONNECTION=sync in tests means this all runs inline within the request.

A message only becomes visible to *other* channel participants once `Message::approveModeration()` runs (which is what fires the `MessageSent` broadcast) — the sender always sees their own message regardless of status. Any query surfacing messages to a viewer MUST use `Message::scopeVisibleTo($viewer)` (or `scopeApproved()` for viewer-agnostic contexts like unread counts) — querying `channel->messages()` directly leaks flagged/pending content to other participants. See ChannelController for the pattern (message list, `latestMessage` eager-load constraint, unread count).

Admin review lives at `App\Filament\Resources\FlaggedMessages` (scoped to Pending+Flagged only, not a general message browser) — approving there calls the same `Message::approveModeration()` used by the job, via the shared `FlaggedMessageActions` class.

## Relation-builder ->update() bypasses casts (encryption, etc.)
`$model->relationName()->update([...])` calls `update()` on the relation's *query builder*, not a hydrated model — it issues a raw mass-UPDATE and never runs through `setAttribute()`, so casts (`encrypted`, custom casts, mutators) are silently skipped. For `StudentProfile::parent_name/parent_email/parent_phone` (encrypted since 2026-08-16), this writes plaintext to a column that's supposed to hold ciphertext, and the next read throws `DecryptException: The payload is invalid.`

Always update through a loaded model instance instead: `$model->relationName->update([...])` (no parens — triggers/uses the lazy-loaded model) or `$model->relationName()->first()->update([...])`.

Caught via 3 test call sites (`PingParentTest`, `StudentProfileGdprTest`) using the relation-builder form — fixed by dropping the parens. No production code path was affected, but check for this pattern before adding any new `encrypted`/custom cast to an existing column.

## Raw DB::table() reads also bypass casts, not just relation ->update()
Extends the ->relation()->update() note above: casts (encrypted, custom, etc.) only apply when going through a hydrated Eloquent model. A raw `DB::table('badge_user')->join('users', ...)->get(['users.name as ...'])` returns the literal column value — for `User::name` (encrypted since 2026-08-16) that's ciphertext, rendered straight into the UI.

Found live in `RecentActivityWidget::badgesAwarded()` (2026-08-17) — it joined `users` directly to grab `users.name` for the "X earned badge Y" feed, so the admin dashboard displayed raw base64 ciphertext instead of the student's name. Fixed by dropping the `users` join, selecting only non-encrypted columns (`user_id`, badge name, timestamp) from the raw query, then resolving names via one batched `User::whereIn('id', ...)->get()->keyBy('id')` lookup — avoids N+1 while still decrypting correctly.

Rule of thumb: before writing a raw `DB::table()`/query-builder join or select that touches a column with a cast, ask whether it needs to be an Eloquent read instead (or a batched follow-up query) — no test unless you specifically assert on the resolved value would catch this, since the query itself doesn't error.

## LessonQuiz/LessonQuizQuestion are distinct from the certification Quiz/QuizQuestion
Two unrelated "quiz" concepts coexist — don't conflate them or reuse table/model names across them:

- `Quiz`/`QuizQuestion` (tables `quizzes`/`quiz_questions`) — the teacher certification quiz, one per Course, gates whether a teacher can be assigned to teach it. `correct_option` is an integer index into `options`.
- `LessonQuiz`/`LessonQuizQuestion` (tables `lesson_quizzes`/`lesson_quiz_questions`) — a student-facing quiz per Lesson, generated by `QuizGenerationService` from `LessonSlideshow::slides_text` (falls back to `Lesson::reading_content`). `correct_answer` is the correct option's literal string value, not an index. Has draft/published status (`LessonQuizStatus`) — students only ever see published ones, enforced via `LessonQuizPolicy` and `LessonQuiz::scopePublished()`, not just hidden in the UI.

Added 2026-09-05. If a future ask says "quiz" for lesson-level content, it means `LessonQuiz`, not `Quiz`.

## Admin-configurable settings go through SettingKey + Setting, not config() or new tables
There is one settings mechanism (added 2026-09-05, first of its kind). Don't add a second, and don't reach for `config()` for anything an admin should be able to change at runtime.

To add a setting: add a case to `App\Enums\SettingKey` with its `default()`, `label()`, `helperText()` and `section()`, then give it a form component in `App\Filament\Pages\Settings::componentFor()` and a cast in `castValue()`. It appears on /admin Settings automatically — no migration, no new page.

Read with `Setting::get(SettingKey::Foo)` (falls back to the enum default when no row exists), write with `Setting::set(...)` (busts the cache). A row only exists once an admin saves.

Trap: the `value` column is JSON-cast, and all settings are cached as one array. `Setting::cached()` deliberately uses `static::all()` + `mapWithKeys`, NOT `pluck('value','key')` — a query-builder pluck bypasses the cast and returns raw JSON strings. Same casts trap documented above for raw DB reads; don't "optimize" it into a pluck.

## Looking up an encrypted column by exact value needs a blind-index hash column
An `encrypted` cast (User::name, StudentProfile's old parent_* fields, ParentContact::{name,email,phone}) uses a random IV per write, so `WHERE column = ?` can never match its ciphertext — this is why encrypted columns are already excluded from Filament search (see .ai/rules/filament-resources.md).

If a feature genuinely needs exact-match lookup against an encrypted value (not just display), add a separate indexed `{column}_hash` string column: HMAC-SHA256 of the plaintext keyed off `config('app.key')`, written only by a model observer alongside the encrypted value it indexes (never fillable/settable directly, so it can't drift out of sync). Never make the hash column itself encrypted or displayed — it's a lookup key only.

See ParentContact.email_hash/phone_hash (added 2026-09 for the "request a preferences link by email/phone" flow) for a full worked example, including the observer that maintains them.
